# История разработки

## Первоначальный промт

Ты senior Python developer. Реализуй простую, надёжную и полностью рабочую консольную утилиту на Python для проверки ссылок в Markdown-файлах.

Не усложняй решение сверх требований. Нужен небольшой понятный CLI-скрипт, который можно запустить на macOS через `python3`.

Важное требование: задача не заканчивается написанием кода. После реализации обязательно запусти программу, протестируй её и исправь обнаруженные проблемы. Итоговый результат должен быть реально проверен запуском.

### Задача

Скрипт получает путь к директории:

```bash
python3 checker.py ./my-project
```

После запуска он должен:

1. Рекурсивно найти все `.md` файлы.
2. Разобрать Markdown с помощью настоящего Markdown-парсера.
3. Извлечь ссылки.
4. Определить тип каждой ссылки.
5. Проверить локальные ссылки на существование.
6. Проверить HTTP/HTTPS ссылки сетевым запросом.
7. Выполнять HTTP-проверки параллельно с ограничением количества одновременных запросов.
8. Вывести краткий цветной отчёт.
9. Детально показать максимум 10 сломанных ссылок.
10. После реализации самостоятельно запустить и протестировать программу.
11. Если программа работает неправильно — найти причину, исправить код и повторить запуск.

### 1. Markdown-парсинг

Для извлечения ссылок использовать настоящий Markdown-парсер вместо регулярных выражений.

Предпочтительный вариант: `markdown-it-py`. Также допустим `mistune`, если для решения задачи он объективно подходит лучше.

Не использовать regex как основной способ разбора Markdown.

Парсер должен корректно находить реальные Markdown-ссылки и изображения:

```markdown
[Documentation](https://example.com/docs)
[Local file](../docs/manual.pdf)
![Logo](./images/logo.png)
```

Конструкции, похожие на ссылки, но находящиеся внутри fenced code blocks или inline code, не должны считаться ссылками, например:

````markdown
```text
[Fake link](https://example.com/not-a-real-link)
```

`[Fake link](https://example.com/not-a-real-link)`
````

Эти ссылки проверять не нужно.

Для каждой реально найденной ссылки сохранить: markdown-файл, номер строки, оригинальный URL/path, информацию, необходимую для проверки и отчёта.

Если выбранный Markdown-парсер не предоставляет номер строки непосредственно для конкретной ссылки, реализовать получение номера строки надёжным способом с использованием структуры/token map парсера. Не возвращаться к полному regex-парсингу Markdown только ради определения номера строки.

### 2. Поддерживаемые ссылки

- HTTP/HTTPS: `https://example.com/page`, `http://example.com/page`
- `file://` URI: `file:///Users/user/project/file.pdf`
- Относительные локальные пути: `./images/logo.png`, `../docs/manual.pdf`, `images/photo.jpg`
- Абсолютные локальные пути: например `/Users/user/project/file.txt`

### 3. Поиск Markdown-файлов

Переданный пользователем путь — корневая директория проверки. Рекурсивно найти внутри неё все файлы с расширением `.md`. Скрипт только читает Markdown-файлы и не должен их изменять. Если отдельный `.md` файл невозможно прочитать, обработать ошибку и продолжить работу с остальными файлами.

### 4. Относительные локальные ссылки

Относительный локальный путь должен разрешаться относительно директории Markdown-файла, в котором находится ссылка, а не относительно директории запуска `checker.py`. Для локальной ссылки проверить существование соответствующего файла или директории средствами Python.

### 5. file://

Поддерживать `file:///...`, преобразовывать URI в локальный filesystem path и проверять его существование, включая URL encoding (`%20` → пробел и т.п.).

### 6. Fragment и query

Для локальной ссылки вида `../docs/manual.md#installation` проверять существование `../docs/manual.md`. Ссылки вида `#installation` (только внутренний anchor) не проверять как файл или HTTP URL. HTTP/HTTPS URL с query parameters и fragments должны корректно обрабатываться.

### 7. Проверка HTTP/HTTPS

1. Выполнить `HEAD`.
2. Разрешить redirects.
3. Использовать timeout 5 секунд.
4. Если `HEAD` возвращает `403` или `405`, выполнить fallback через `GET`.
5. Обработать результат.
6. Продолжить проверку остальных ссылок независимо от результата.

Использовать нормальные HTTP headers (`User-Agent`, `Accept`), browser-like `User-Agent`. Не пытаться обходить CAPTCHA, Cloudflare challenge или серьёзные anti-bot механизмы.

### 8. HTTP-статусы и сетевые ошибки

Корректно обрабатывать как минимум: HTTP 404, HTTP 500, Timeout, DNS error, Connection error, Network error. HTTP `2xx` — успех. Redirect на успешный ресурс — успех. `404`, `410`, `5xx` и другие явные HTTP-ошибки — сломанная ссылка. Timeout/DNS/connection — тоже ошибка проверки. Ошибка одной ссылки не должна останавливать проверку остальных. Для HTTP-ошибок сохранять status code.

### 9. Ограниченная параллельность

HTTP/HTTPS ссылки проверять параллельно, максимум 5 одновременных запросов (`MAX_CONCURRENT_REQUESTS = 5`), предпочтительно `concurrent.futures.ThreadPoolExecutor(max_workers=5)`. Не создавать неограниченное количество потоков/задач. Локальные проверки — без сетевого ограничения.

### 10. Повторяющиеся HTTP URL

Каждый уникальный HTTP/HTTPS URL проверяется один раз, результат переиспользуется для всех вхождений. `Links checked` при этом отражает все вхождения, а не только уникальные URL.

### 11. Информация о ссылке

Для каждой ссылки сохранить: markdown-файл, номер строки, оригинальный URL/path, причину ошибки, HTTP status code (если есть). Путь к markdown-файлу в отчёте — относительно проверяемой корневой директории.

### 12. Цветной вывод

ANSI colors без сторонних библиотек: зелёный — успешный итог, красный — `BROKEN`/4xx/5xx/количество сломанных ссылок, жёлтый — timeout/DNS/connection/network errors, cyan — информационные значения, стандартный цвет — пути и URL. После цветного участка обязательно `RESET`.

### 13. Формат отчёта

Не выводить каждую рабочую ссылку. После проверки показать `Links checked` и `Broken links`, детально — максимум первые 10 сломанных ссылок (`BROKEN`, файл, строка, ссылка, причина). Если сломанных больше 10 — после десятой вывести `...` и `Showing 10 of N broken links.`

### 14. Если ошибок нет

`Broken links: 0` и `No broken links found.` — зелёным.

### 15. Надёжность

Скрипт не должен полностью падать из-за одной проблемной ссылки или Markdown-файла: timeout, DNS failure, connection failure, HTTP errors, отсутствующий локальный файл, некорректная ссылка, проблемы чтения `.md` файла — всё обрабатывается, проверка остальных ссылок продолжается.

### 16. Технологии

Python 3, `requests`, `markdown-it-py`, `pathlib.Path`, `concurrent.futures.ThreadPoolExecutor`. Regex допустим только как вспомогательная техника, не заменяющая разбор через parser. Type hints обязательны. Без избыточной архитектуры.

### 17. requirements.txt

Все зависимости в `requirements.txt`, минимум `requests` и `markdown-it-py`, без лишнего.

### 18–20. Обязательный запуск, тестирование, доводка и финальный результат

Написанием файлов задача не заканчивается — обязательно самостоятельно создать тестовую директорию с разными кейсами (существующий/несуществующий файл, вложенные относительные пути, `file://`, URL-encoding, рабочий/404 HTTP, дубликаты URL, fenced/inline code, `#anchor`, >10 сломанных ссылок), запустить, проверить корректность, при необходимости исправить код и повторить цикл до рабочего результата. Не оставлять TODO/заглушки/псевдокод. В конце — краткая инструкция для macOS (`python3 --version`, `pip install -r requirements.txt`, `python3 checker.py ./my-project`) и честный отчёт о том, что реально было протестировано.

## Доработки после первого запуска

После первоначальной реализации в реальном использовании обнаружились и были исправлены баги, а также добавлена новая возможность:

- **Баг с кириллицей/пробелами в локальных ссылках.** `markdown-it-py` percent-encode'ит href для всех ссылок, а не только для `file://`. Декодирование (`unquote`) было реализовано только для `file://`-схемы, из-за чего локальные ссылки на файлы с кириллическими именами (например, `../Настройка и конфигурация/Установка и запуск.md`) не находились на диске и ошибочно помечались как `Local file not found`. На реальном репозитории это давало 44 ложных срабатывания из 46 «сломанных» ссылок. Исправлено: декодирование теперь применяется и к обычным локальным путям, а также уточнено определение номера строки и отображаемого пути в отчёте (показывается читаемый декодированный путь вместо `%D0%90...`).
- **Поддержка загрузки удалённого (remote) git-репозитория по URL.** Изначально скрипт принимал только локальную директорию. Добавлена возможность передать первым аргументом публичный git URL (`https://...`, `git@...`, `ssh://...`, `git://...` или что-то, заканчивающееся на `.git`) — скрипт сам клонирует репозиторий (`git clone --depth 1`) во временную директорию, проверяет ссылки и гарантированно удаляет клон после завершения (в том числе при ошибке). Также добавлена нормализация web-ссылок вида `https://github.com/user/repo/tree/main` (не являющихся валидным clone URL) — из них автоматически извлекается репозиторий и ветка (`git clone --branch <branch>`). Обработаны сценарии: git не установлен, таймаут клонирования, несуществующий/приватный репозиторий.

Оба изменения проверены реальными запусками (в том числе на публичных GitHub-репозиториях и на приватной базе знаний пользователя), после исправлений результаты подтверждены вручную через `curl`/`ls`.
